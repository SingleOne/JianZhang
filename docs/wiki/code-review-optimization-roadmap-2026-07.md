# 代码审查优化执行路线图（2026-07）

> 来源：[代码审查报告](./code-review-2026-07.md)
>
> 目标：将审查建议拆成可以逐项实现、验证和提交的独立任务。
>
> 原则：优先保障用户数据和计算正确性，再进行结构重构，最后处理样式与低收益整理。

## 一、执行规则

- 每次只实施一个编号任务，避免多个重构相互影响。
- 涉及重构时先补充现有行为测试，再移动代码，不顺带改变业务逻辑。
- 每项任务单独提交，提交信息应能说明该项优化的实际内容。
- 不对全项目进行一次性格式化，避免产生难以审查的大规模无关差异。
- 不主动引入新的状态管理方案；现有组件完成拆分后再评估是否确有需要。
- 正式打包仍遵循项目的提交和版本号规则；开发验证不等同于正式打包。

### 6. 统一 K 线缓存容量和清理策略

**目标**

控制用户查看大量股票后产生的渲染层内存、主进程内存和历史磁盘缓存增长。

**实施内容**

- [ ] 为渲染层 K 线缓存增加 LRU 上限，建议最多保留 50～100 个“股票+周期”条目。
- [ ] 为 `KlineHub` 实时缓存增加相同或相近的容量限制。
- [ ] 为 `HistoricalKlineCache` 内存条目增加淘汰策略。
- [ ] 为历史 K 线磁盘缓存增加按最后访问时间清理机制，建议保留最近 90 天。
- [ ] 保持同参数请求合并、实时30秒缓存和历史K线新鲜度规则不变。
- [ ] 为缓存命中、过期、淘汰、回退和请求合并补充测试。

**验收标准**

- 缓存条目超过上限后优先淘汰最久未使用的数据。
- 缓存淘汰不会影响当前展开股票和筹码分布计算。
- 删除过期磁盘缓存不会删除仍在有效期内的数据。
- 行情接口请求频率不会因缓存调整而升高。
