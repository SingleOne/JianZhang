# AI 记忆与资料库详细设计：本地独立服务版

状态：总体设计与阶段进度；A、C 已交付，D 核心能力已编码但尚未人工验收，B 自动维护已编码、待真实模型与界面验收；E 导出恢复暂未实现。阶段实现进度不等于运行验收通过。

当前已扩展到 B 阶段自动维护与 D 阶段资料库核心能力。下文 A–E 是完整设计目标；尚未验收和未实施的内容在第 19 节标明。

本版替代此前“先在见涨进程内实现记忆内核”的部署方案：第一版即提供可独立启动的记忆服务，见涨通过 HTTP API 接入。借鉴精简用户画像、按需历史检索、Agent 主动维护记忆和运行生命周期接入四个机制，不照搬 Hermes 的存储结构。

## 1. 本阶段的明确边界

1. 见涨现有 AI 功能保持不变：对话 Provider、模型选择、用户 API Key、股票数据读取、官方资料搜索、流式输出和现有分析任务继续走原有路径。
2. 记忆是可选增强：开启后为聊天补充用户记忆、会话记忆和资料依据；关闭或服务不可用时，普通聊天仍可使用。
3. 第一版必须真正区分用户，用户之间的画像、历史、文件、检索、任务及导出相互隔离。
4. 第一版不做账号注册、密码、短信、登录页面、订阅和支付。使用服务本地创建的用户身份和连接令牌。
5. 记忆系统独立进程、本地启动；第一版即提供版本化 HTTP API、OpenAPI 描述和接入示例，不把标准接口推迟到后续。
6. 完整方案最终包含用户记忆、会话记忆、历史检索、可检索资料库、删除联动、管理界面和导出恢复；当前已扩展实现 B 与 D 的核心能力，导出恢复仍待 E 阶段。
7. 云端部署、正式账号、收费和高级 Agent 接入只列入本文最后的后续步骤，完成本阶段后再讨论具体实现。

“现有 AI 不变”指保留既有功能、权限、调用方和配置，而不是要求零接入代码或启用记忆后回答逐字不变。新增代码集中在聊天生命周期、工具路由、上下文和管理界面；不将整个聊天搬到记忆服务。

## 2. 总体架构与职责

```text
见涨 Electron 客户端                       本地记忆服务（独立进程）
┌─────────────────────────┐               ┌───────────────────────────┐
│ 原有 AI 对话和 Provider   │               │ HTTP API / 身份解析 / 权限 │
│ 原有股票工具和分析任务     │               │ MemoryEngine              │
│ 新增记忆与资料管理界面     │               │ 用户画像 / 会话回忆        │
│ 新增 MemoryClient        │ ──HTTP/JSON──>│ 文档导入 / 检索 / 引用     │
│ 主进程保存连接凭证         │ <──结果与状态──│ 维护任务 / 模型适配         │
└────────────┬────────────┘               └─────────────┬─────────────┘
             │                                           │
     原有对话模型供应商                          SQLite + 文件目录
                                                 可配置的维护/向量模型
```

职责划分：

| 事项     | 见涨负责                                  | 记忆服务负责                           |
| -------- | ----------------------------------------- | -------------------------------------- |
| 最终回答 | 按当前 Provider 和 API Key 生成、流式展示 | 返回所需上下文，不代替主对话模型       |
| 原始聊天 | 继续使用现有本地会话存储                  | 保存获准同步的消息副本和检索投影       |
| 用户记忆 | 展示、编辑入口、调用工具                  | 存储、版本、提取、检索和删除           |
| 资料文件 | 用户选择、通过 API 上传、展示来源         | 保存原文件、解析、分块、索引和版本管理 |
| 股票业务 | 继续沿用当前数据授权和工具                | 不读取持仓数据库，不执行交易操作       |
| 身份     | 保存连接配置，展示服务确认的用户          | 验证令牌，决定 userId、clientId 和权限 |
| 生命周期 | 同步消息、准备上下文、传递取消和删除事件  | 幂等处理、维护派生数据、报告状态       |

服务不直接打开见涨的数据目录，也不导入 Electron、React 或股票业务代码。这样换成远程地址或其他 Agent 时，不需要推翻核心数据模型。

## 3. 工程与源码边界

两个工程现已分开；见涨仓库公开，AI-Memory-Service 仓库应保持私有。下面名称和路径仍可因部署环境调整。

```text
  src/modules/ai/main/memory/           HTTP 客户端、同步队列、工具桥接
  src/modules/ai/shared/                接口类型、状态和引用类型
  src/modules/ai/renderer/              连接设置、记忆、资料库、来源界面

memory-service/                        独立工程，核心代码按私有方式管理
  src/core/                            归属规则、记忆、检索、生命周期
  src/http/                            HTTP 路由、身份、校验、OpenAPI
  src/storage/                         SQLite、迁移、文件存储
  src/documents/                       解析、分块、版本发布
  src/models/                          维护模型与向量模型适配
  src/jobs/                            持久化任务、重试、检查点
  src/cli/                             初始化、本地用户、令牌、启动
  examples/                            标准 HTTP 接入示例
```

接口契约及客户端可以公开；核心源码不应为了本地调试放进公开仓库再忽略。实际开发时先确定私有工程位置和源码管理方式，本阶段不自动创建远端仓库、不改变见涨许可证。

首版采用 TypeScript + Node.js，HTTP 层提供 JSON 和文件上传接口；SQLite 保存业务状态，后台 worker 处理解析和向量计算。框架、驱动和模型依赖在实施时选定兼容版本并锁定，不要求用户运行 Docker、Redis 或独立向量数据库。

MemoryEngine 保持不依赖 HTTP 的接口边界，服务内直接调用。未来自建服务端 Agent 可以嵌入同一内核，其他语言客户端通过 API 接入。

## 4. 无账号系统时的用户身份

### 4.1 用户身份与账号分离

用户是稳定的数据归属主体，不等于登录账号、显示名称、Windows 用户名或设备编号。

| 标识         | 含义                         | 分配和信任来源                     |
| ------------ | ---------------------------- | ---------------------------------- |
| serviceId    | 一个记忆服务数据实例的标识   | 服务初始化生成，普通重启不变       |
| userId       | 记忆数据所属用户             | 服务本地管理命令创建的随机稳定 ID  |
| clientId     | 一个接入客户端的稳定命名空间 | 管理命令创建，并绑定凭证           |
| agentId      | 调用方 Agent 的逻辑身份      | 服务配置并绑定凭证，用于追溯和授权 |
| credentialId | 某份可轮换、可撤销的连接凭证 | 服务签发，不能作为用户主键         |

首次初始化可以创建“本地用户”和“见涨客户端”，签发一份随机高熵令牌。之后可再创建用户 B，并签发另一份凭证，验证同一服务支持多个用户而不会串数据。

令牌在服务端只存不可逆摘要及其绑定关系，客户端在主进程中安全保存。普通 API 没有开放注册或自选身份入口；用户创建、令牌签发和撤销通过本机管理命令执行。

服务把令牌解析为可信调用者：

```ts
type TrustedPrincipal = {
  userId: string
  clientId: string
  agentId: string
  scopes: string[]
}
```

业务方法只接受这个可信身份，不接受模型传入的任意 userId。将请求体里的 userId 改为别人的 ID，不会改变访问主体。

### 4.2 本地初始化使用方式

以下是拟实现的 CLI 形状，并非现有可执行命令：

```text
memory-service init --data-dir <独立数据目录>
memory-service user create --name "本地用户"
memory-service credential issue --user <userId> --client jianzhang
memory-service serve --host 127.0.0.1 --port 43127
```

见涨新增连接设置：服务地址、连接令牌、连接名称、测试连接、启用记忆。测试成功后展示服务返回的用户名称和身份摘要，不要求用户手填 userId。

43127 只是建议默认端口，可以配置；占用时明确报错，不自动连接其他端口上的未知服务。首次连接记录 serviceId，后续同地址出现另一实例时暂停同步并要求重新确认，不把旧队列发给新服务。

### 4.3 权限与本阶段安全边界

默认凭证可读写自己的用户记忆、管理自己的资料库和本客户端会话。跨客户端历史检索单独授予，且被检索会话本身必须允许共享；只读 Agent 可以获得不含写权限的凭证。

用户隔离覆盖查询、来源读取、文件下载、任务状态、操作历史、导出、缓存和后台任务，不能只给主表增加一个 userId。

本地凭证是“持有者可访问”的授权方式，不是正式账号登录，也不能防止有权限读取本机数据目录和凭证的人访问数据。本阶段不宣称实现见涨整个应用的多账号隔离，更不把本地模式直接当成公网生产方案。

## 5. 标准连接协议

第一版选择版本化 HTTP API + JSON，使用 OpenAPI 3.1 描述请求、响应、错误、文件上传和安全方案。这是基于标准协议的自定义记忆接口，不宣称存在所有 Agent 都已实现的统一记忆协议。[OpenAPI 规范](https://spec.openapis.org/oas/v3.1.1.html)

连接示例：

```http
GET /v1/me HTTP/1.1
Host: 127.0.0.1:43127
Authorization: Bearer <local-access-token>
```

成功响应包含 serviceId、userId、clientId、agentId、显示名称和授权范围。能力接口另外返回 apiVersion、schemaVersion、支持的文件类型、检索和维护能力状态。

约定如下：

- 默认只监听 127.0.0.1；请求由 Electron 主进程发起，renderer 不直接拿到令牌。
- 第一版本地 HTTP 是受限的单机开发模式；采用 Bearer 头形式并不等于实现了 OAuth 登录。RFC 6750 的完整使用要求 TLS，后续非回环地址必须使用 HTTPS，不能照搬明文配置。[RFC 6750](https://www.rfc-editor.org/info/rfc6750/)
- 不把令牌放进 URL、普通日志和导出包，不跨主机跟随携带凭证的重定向；默认不开放浏览器跨域访问。
- 所有业务路由验证身份与资源归属。无权对象不泄露正文或归属信息；上传接口不接受客户端提供任意服务端文件路径。
- 写请求使用 operationId 做业务幂等；相同 ID 与不同内容组合返回冲突。去重范围至少包含 userId 和 clientId。
- 更新带 expectedRevision，冲突返回 409；参数错误 400、凭证错误 401、能力不允许 403、对象不可见 404、任务/服务暂不可用 503。
- 长任务返回 202 和 jobId，通过任务接口查询；失败返回可展示的原因，不用一个 success 字段掩盖“只入队尚未完成”。
- 同一 /v1 内只做兼容新增；客户端先检查能力，不支持的版本拒绝启用记忆，普通 AI 不受影响。

首版不要求 WebSocket、MCP 或特定 Agent SDK。提供 TypeScript HTTP 客户端及一份不依赖见涨的接入示例即可证明可复用。

## 6. 数据层级与归属

| 类型         | 内容                                               | 使用范围                                 | 删除语义                                 |
| ------------ | -------------------------------------------------- | ---------------------------------------- | ---------------------------------------- |
| 用户长期记忆 | 稳定背景、偏好、长期目标、明确长期要求             | 同一用户的授权会话与 Agent               | 独立管理，不因一个来源会话删除而自动删除 |
| 会话记忆     | 该会话消息副本、摘要、临时限制、未决问题、历史索引 | 当前会话；允许共享时可按需被其他会话检索 | 随所属会话删除                           |
| 资料库       | 用户长期保存的文件、正文、索引和版本               | 同一用户授权范围内，会话选择启用哪些库   | 随文档或资料库删除                       |
| 会话附件     | 只服务于某次讨论的文件                             | 仅所属会话                               | 随会话删除                               |

会话附件复用资料处理流水线，但不是另一套长期记忆。来源会话 A 被 B 引用，不意味着把 A 的内容自动变成 B 的永久资料。

普通会话可默认允许同用户授权历史检索，设置中可关闭；附件始终不随跨会话历史检索扩散。需要长期共享时，用户明确执行“加入资料库”。

用户长期记忆一旦独立保存，就与临时会话记忆不同。删除会话时界面明确提示长期记忆和全局资料会保留；想忘记长期事实，需要删除对应用户记忆，不能含糊地宣称删除会话会抹去所有已形成的信息。

| 实体                         | 核心字段及作用                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------ |

| ClientCredential             | credentialId、tokenHash、userId、clientId、agentId、scopes、revokedAt                      |
| ProfileFact                  | userId、id、key、content、category、revision、status、pinned、sources、expiresAt           |
| ProfileSnapshot              | userId、profileRevision、text、factIds；可重建精简画像                                     |
| Session                      | userId、id、clientId、externalSessionId、generation、revision、historyVisible、deletedAt   |
| MessageReplica               | userId、sessionId、externalMessageId、revision、role、status、text、occurredAt、sourceRefs |
| SessionSummary               | userId、sessionId、sourceRevision、throughSequence、text、evidenceRefs                     |
| HistoryChunk                 | userId、sessionId、messageIds、role、timeRange、text、sourceRevision                       |
| Library                      | userId、id、name、revision                                                                 |
| Document / DocumentVersion   | userId、documentId、ownerType、ownerId、versionId、hash、status、activeVersionId           |
| DocumentChunk                | userId、documentId、versionId、text、headingPath、locator、contentHash                     |
| Embedding                    | userId、sourceKind、sourceId、sourceRevision、modelFingerprint、dimension、vector          |
| ContextBundle / ContextUse   | userId、sessionId、turnId、sourceRefs、usedVersions、createdAt；正文短期使用               |
| Job / OperationReceipt       | userId、targetId、sourceRevision、operationId、state、checkpoint、errorCode                |
| DeletionRecord / ChangeEvent | userId、targetId、generation、revision、eventCursor；失效与重连同步依据                    |

内部会话唯一关系采用 (userId, clientId, externalSessionId, generation)，避免多个应用使用相同会话编号。agentId 用于来源和授权，不自动决定用户是谁。

所有用户数据仓储方法都要求 TrustedPrincipal 或明确的受限 userId 上下文。跨表关联使用带 userId 的约束或等价校验，防止把 A 的片段关联到 B 的文档；后台任务同样不得丢失该上下文。

SourceRef 区分用户手工输入、历史消息、文档版本及应用快照引用。原始内容是依据，画像概要、摘要、全文和向量索引都是派生数据，不能只保存向量而丢弃原文。

## 8. 精简用户画像与主动维护

### 8.1 存储和使用

每条事实单独存储，概要按版本生成。固定偏好和高频背景组成少量核心画像，其余条目按当前问题检索，不每次把整个用户档案塞给模型。

例如“回答先给结论”可成为用户偏好；“本次只讨论银行股”留在会话；“现在可用资金有多少”继续读取见涨实时数据，不存成长期余额。

每轮开始读取当前 profileRevision。其他会话或 Agent 的修改从下一轮生效，不在同一次生成中途替换画像。当前用户明确要求优先于旧偏好，手工固定内容不由自动维护擅自覆盖。

### 8.2 两条写入路径

1. 显式写入：用户通过管理界面编辑，或在对话里要求“记住/修改/忘记”，Agent 调用结构化工具；收到服务成功结果后才确认保存。
2. 自动维护：消息同步成功后，服务对新增用户陈述进行增量提取，并更新会话摘要；不反复提交全部历史。

自动提取区分长期事实、临时约束、假设、助手建议和资料内容。只有具有明确依据的长期用户信息才能保存；不确定的候选保持待确认，不按模型置信度直接变成事实。

维护任务可按累计新增内容和摘要预算触发，不强制每轮多调用一次模型。一次调用可同时提出画像候选和摘要；结构化结果通过归属、来源、版本和类型校验后才提交。

同一 key 使用 revision 控制冲突；用户更正优先，过时任务重新读取后再判断。删除或拒绝条目时保存必要的非正文处理标记，阻止同一批旧消息立即重新提取；用户之后明确重述可重新保存。

普通回答里的“我记住了”不是持久化凭据。失败或超时的写入显示真实状态；如果请求结果未知，先按 operationId 查询，而不是换 ID 盲目重试。

## 9. 会话记忆与历史检索

见涨继续保存原始 JSONL 消息；服务保存用户允许同步的消息副本。这是通过网络接口接入时必要的数据边界，不再假设服务可以打开客户端磁盘。

当前会话使用“近期完整轮次 + 较早内容的滚动摘要”。摘要记录已覆盖序列和源版本，保存成功才推进检查点；滞后的摘要不能替代尚未覆盖的原文。

服务保留同步消息的 role、status、时间和来源。失败或停止的助手回答可以作为带状态的历史记录，但不作为已确认结论；已成功执行的明确记忆写入不因后续回答失败而回滚。

历史检索在用户询问过去讨论、引用省略对象或 Agent 判断需要时执行。先检索当前会话，需要时再检索同用户、授权且允许共享的其他会话；普通问题不默认扫描全部历史。

摘要可用于发现相关会话，重要断言必须能回到原消息。命中结果返回原会话、时间、角色、片段、消息 ID 和来源版本，不把模型当年的建议当成实际发生的交易。

来自外部会话或文档的引用也要随 MessageReplica 保存依赖关系。派生摘要不能通过复制内容绕过来源失效规则；历史回答原文仍按其所属会话保存，但重新检索时标明相关外部证据已失效，不把它当作仍然有效的原始证据。

## 10. 资料库流水线

```text
选定用户与归属 → 上传文件 → 暂存与校验 → 保存原文件
→ 解析正文和位置 → 结构化分块 → 全文索引 → 向量化
→ 发布活动版本 → 可检索和引用
```

第一版完整支持 TXT、Markdown、文字型 PDF、DOCX。扫描 PDF 检测到缺少文本后显示“需要 OCR”；OCR、复杂财务表格还原和 XLSX 结构问答放在后续，不伪装为已支持。

解析保留标题和段落边界。PDF 保留页码，DOCX 使用标题路径、段落或表格位置，不编造不稳定的页码。未可靠提取的表格标记限制，不能承诺精确财务表格问答。

分块优先按章节、段落和表格单元组织，长段落再拆分。约 400–800 token/块和少量重叠可作为调优起点，不是固定格式要求；引用回到原始定位而非分块编号本身。

文件管理规则：

- 通过上传字节传输，见涨的本地绝对路径不作为服务读取入口。服务生成存储路径，原文件名仅作元数据。
- 用户删除原电脑文件后，已入库副本仍可用；界面明确这是独立副本。
- 同一归属下按内容哈希识别重复，不跨用户暴露重复文件情况；首版不做跨用户物理去重。
- 普通导入创建新文档；只有明确“替换版本”才更新现有文档。
- 新版本在配置所要求的索引阶段完成后原子切换。混合检索模式下向量失败保留旧活动版本，用户可明确选择以关键词模式发布新版本。
- 旧引用固定到旧版本；历史版本默认不参与新检索，可单独清理。删除文档清理所有版本。

状态至少区分：排队、解析中、全文已就绪、向量处理中、完整就绪、需要 OCR、失败。没有配置向量能力时允许以“关键词模式”使用，不能显示“语义检索就绪”。

## 11. 检索、上下文与引用

### 11.1 检索流程

1. 根据凭证固定用户及授权范围，再验证当前会话和选定资料库。
2. 保留股票代码、公司名、年份等精确信息，构造关键词和语义查询。
3. 在相同有效范围中执行全文与向量检索；过滤失效、删除和非活动文档版本。
4. 使用排名融合、去重及少量相邻内容扩展，限制单一文档占用。
5. 根据预算返回片段和引用；需要更多证据时由 Agent 调用 read_source。

中文全文检索使用入库和查询一致的分词接口，包含短词、代码、日期和英文缩写测试。SQLite FTS5 默认分词不能直接当作完整中文方案，trigram 也不能覆盖所有短查询。[SQLite FTS5](https://www.sqlite.org/fts5.html)

首版向量基线可将向量存入 SQLite，并在已授权有效集合内做精确相似度计算，避免增加独立向量服务。复杂度随用户资料量增长，需要记录耗时；不能先全局取 Top-K 再删除无权结果。数据量扩大后替换索引实现，不改变 API。

嵌入模型版本、维度、预处理和查询前缀共同构成 modelFingerprint。不同模型空间不能混合比较；切换模型后台重建，新索引完成前保留可用的旧索引或明确降级。

### 11.2 上下文预算

服务返回 ContextBundle，而不是直接替换见涨的完整提示词：包含画像、摘要、检索证据、来源 ID、源版本和降级状态。

见涨负责最终预算：先保留系统规则、输出预留、工具定义、当前问题和必要近期轮次，再分配记忆材料。可将记忆材料 8,000 token、画像 1,000、摘要 1,500 作为大窗口模型的初始上限，但必须受实际剩余窗口约束，不要求填满。

保留完整轮次和工具调用/结果对应关系，不依据“16 条消息”推断 token 数。小窗口或模型能力不明时降低记忆预算；现有 maxContextMessages 仍作为近期消息数量配置，不因接入记忆而改写用户设置。

记忆和文档内容作为有来源的背景数据，不具有覆盖系统规则、改变用户权限或诱导工具越权的效力。当前账户和行情以原有股票工具实时读取结果为准。

### 11.3 引用

历史、文档、用户记忆和现有官方搜索分别使用明确来源类型，引用编号不能冲突。只有本轮实际提供给模型的来源才能进入回答引用列表。

文档引用包含文件名、版本、页码/标题/段落；历史引用包含会话和消息时间。主进程核对引用 ID，正文是否真正支持结论仍需效果评估，不能把“ID 合法”当成“回答正确”。

ContextUse 长期保留必要 ID 和版本，不为调试再次永久保存全部上下文正文。来源已删除时显示不可定位，不能绕过权限用旧下载地址或缓存继续读取。

## 12. 维护模型与向量模型配置

三种职责独立：

| 模型职责               | 执行位置          | 配置来源                   |
| ---------------------- | ----------------- | -------------------------- |
| 生成最终聊天回答       | 见涨现有 Provider | 原有见涨配置和凭证，不改动 |
| 提取长期记忆、生成摘要 | 记忆服务          | 独立维护模型配置           |
| 入库和查询向量化       | 记忆服务          | 独立 embedding 配置        |

首版服务实现一种实际可用的文本维护适配和一种实际可用的向量适配，并提供可替换端口；优先支持可配置 HTTP 模型端点。端点可以是本机推理服务，也可以是用户明确配置的在线服务，不强制更换见涨聊天模型。

维护模型和向量模型需要独立配置端点、模型标识和凭证引用。服务从受保护的本地配置/环境读取秘密，业务接口只返回配置状态；不自动复制见涨现有 API Key，不把密钥写进同步事件。

没有维护模型时，手工管理、显式结构化记忆工具、消息保存和关键词检索仍可运行，但自动提取/语义摘要状态为未配置；没有向量模型时仅提供关键词检索。完整交付要在已配置模型条件下具备自动维护和混合检索能力，不能把“可配置”当成已完成实现。

服务本地运行不等于所有数据都不出电脑：在线维护/向量服务会收到所需文本，见涨的在线对话模型会收到选入本轮的记忆。界面分别说明这些路径；完全离线使用需要同时配置可用的本地模型。

后台调用不经过见涨带记忆的聊天入口，避免递归触发维护。记录调用用途、耗时和 token 等可用指标，用于调试成本，不在本阶段实现付费计费。

## 13. 公共 API 设计

以下为拟定接口契约。具体请求字段实施时用 OpenAPI 固化，不能只生成文档而缺少处理逻辑。

| HTTP 接口                                           | 用途                                   |
| --------------------------------------------------- | -------------------------------------- |
| GET /healthz                                        | 最小存活信息，不返回用户和资料内容     |
| GET /v1/me、GET /v1/capabilities                    | 验证连接身份及服务能力                 |
| GET/POST /v1/profile/facts                          | 查询和创建用户记忆                     |

| PATCH /v1/sessions/{id}                             | 修改标题、历史可见性和选定资料库       |
| POST /v1/sessions/{id}/events                       | 同步消息与状态，返回持久化检查点       |
| POST /v1/sessions/{id}/prepare-turn                 | 按预算生成本轮 ContextBundle           |
| POST /v1/search                                     | 搜索已授权的画像、历史和资料           |
| POST /v1/sources/read                               | 按引用读取定位原文，重新校验权限和版本 |

| GET /v1/documents、GET /v1/documents/{id}           | 文档列表、状态和版本信息               |

prepare-turn 请求包含当前会话、turnId、问题、必要近期上下文、可用预算和客户端所知检查点；不携带用户 API Key，不依赖服务器读取客户端文件。临时输入不因准备上下文自动变成持久记忆，持久化通过明确的消息事件完成。

面向聊天模型仅注册三个工具：search_memory、read_source、update_user_memory。工具参数不能传递身份、任意文件路径或扩大授权范围；文档导入、删除整个会话和资料库由界面或可信宿主触发。

未支持工具调用的模型使用每轮预检索和服务独立维护；显示不能主动追加检索的能力限制。支持与否按实际 Provider/模型核验，不凭协议名称推定。

## 14. 见涨一次对话的接入时序

1. 用户打开或新建会话，主进程取得该会话固定的记忆连接绑定，校验服务实例和用户身份。
2. 有待同步删除时优先处理。会话未注册则注册，同步缺失的已落盘消息。
3. 用户发送问题，保留现有本地落盘逻辑，再调用 prepare-turn；该请求有有限等待预算。
4. 服务返回当前画像、可用摘要、需要的资料片段和来源。消息副本尚未追平时返回明确 watermark，不假装已覆盖全部历史。
5. 主进程在原有上下文基础上加入这些背景资料，合并记忆工具与股票/官方搜索工具，然后继续调用原有 Provider。
6. 模型需要补充时，通过工具桥接访问记忆 API；原有股票工具权限及联网搜索开关语义不变。
7. 完整回答先按现有逻辑落盘，再加入同步队列；服务持久化消息后安排索引、摘要和画像维护。
8. 服务更新后推进检查点，下一轮使用新版本。关闭窗口不删除记忆，删除会话才进入删除流程。

所有工具共享本轮调用预算，不因新增记忆工具而成倍增加上限。同一目标写操作按顺序执行，读取可以并行。

## 15. 消息同步、用户切换与故障处理

### 15.1 持久化同步队列

见涨增加轻量本地桥接状态，记录连接、会话绑定、待发送事件和已确认水位。优先复用现有原子文件写入能力；队列保存消息 ID 和必要操作元数据，不另外复制全部聊天正文。

普通消息先落盘再排队，两者不是分布式事务。为覆盖“落盘成功后、入队前崩溃”，启动/重连时按已绑定会话的服务确认水位与本地消息校对并补齐。

事件包含 operationId、外部消息 ID、消息 revision、会话 generation 和客户端顺序号。服务持久化完成才确认；重复投递返回同一结果，缺失或乱序要求补齐，不跨缺口推进摘要覆盖水位。

消息更正或删除通过显式修订事件更新，相关摘要和索引失效。重试回答有独立生成尝试标识，不把已失败的助手内容覆盖成一次成功对话。

### 15.2 连接和用户绑定

一个会话启用记忆后，固定绑定 (serviceId, userId, clientId, externalSessionId, generation)。客户端不能只改当前全局 token，就把原会话继续同步给另一个用户。

第一版连接设置可保存多份配置，但一次选定一个活动记忆身份；不同身份的队列、引用缓存、资料列表和会话绑定分开保存。切换身份中止旧记忆调用，清理临时上下文，不沿用旧画像。

已绑定 A 的会话在 B 配置下不得注入 B 的记忆，也不得把 A 的消息上传给 B；需要继续记忆功能时切回原连接或新建会话。原有本地聊天仍可查看和在关闭记忆后使用，这不等于本应用已经实现账号级本地隐私隔离。

旧会话默认不批量上传。由用户选择“为此会话启用记忆/导入选定历史”，一次明确归属；不会把全部存量历史分别复制给每个新建用户。

### 15.3 不可用与降级

服务未启动、超时或暂时失败：普通 AI 继续，界面提示“本轮未使用记忆”；本地消息继续保存，重连后补同步。默认不使用无法验证有效性的旧上下文缓存。

用户明确询问资料或历史而检索失败时，回答必须说明无法读取相关资料，不能假装已根据文件回答；必要时由用户选择稍后重试。

用户要求“记住/忘记”时，服务不可用不得报告完成。管理界面不悄悄排队一个将来可能不再符合用户意图的未知写操作；同步事件与已明确发起的删除另有持久队列。

401 暂停连接并提示重新配置，版本冲突重新读取，不能对所有错误无限重试。后台任务持久化检查点，重启可继续；永久解析错误保留可解释状态，用户可重试或替换文件。

## 16. 删除语义与离线一致性

| 操作             | 服务端清理范围                                     | 默认保留                              |
| ---------------- | -------------------------------------------------- | ------------------------------------- |
| 删除用户记忆条目 | 条目正文、派生画像和索引、相关缓存                 | 原会话、资料及必要去重标记            |
| 删除见涨会话     | 已同步消息、会话摘要、历史索引、专属附件、相关任务 | 独立用户长期记忆、全局资料库          |
| 清空见涨会话     | 被选中/本客户端对应的会话集合                      | 其他 Agent 会话，不自动清空全用户数据 |
| 删除文档或资料库 | 原文件、所有版本、正文、索引和相关任务             | 已经生成的聊天回答文本                |
| 关闭记忆         | 停止后续读取和同步                                 | 已保存的数据，不等同于删除            |

### 16.1 在线删除

先在见涨持久记录删除意图并阻止该会话新生成和新同步，再提交服务删除。服务事务中标记 tombstone、移出检索范围、使上下文依赖失效并安排文件清理；所有后台写入提交前检查 tombstone 和 generation，防止旧任务复活数据。

服务端逻辑删除确认后，本地原始会话按原有方式删除。数据库与文件系统不共用事务，物理文件清理由持久任务完成；清理未完成显示“已停止使用，文件清理中”，完成后才显示全部清理结束。

同一外部会话的旧事件不能通过重新注册绕过墓碑。用户主动恢复历史时必须使用明确恢复流程和新的 generation，不能被重连重试暗中恢复。

### 16.2 服务离线时删除

本地先持久记录删除意图，再删除本地会话，同时显示“本地已删除，记忆删除待同步”。该连接暂停新的记忆上下文注入，直到删除队列完成；普通聊天仍可继续。

重连时先处理删除，再补同步普通消息。对不确定是否已注册成功的会话，用其固定绑定标识完成查找/删除，不能因本地丢失服务 sessionId 而漏删。

离线客户端无法保证服务副本已立即删除；其他仍连通的 Agent 在服务收到删除前可能继续访问。该限制必须展示，不能把本地队列成功当成跨进程删除完成。

### 16.3 来源失效与边界

服务确认逻辑删除后，新搜索、原文读取、上下文准备均排除来源。客户端通过 change cursor 在新一轮前同步失效信息，长任务期间适度轮询；本客户端发起删除时立即取消相关活动生成。

跨客户端已取得的上下文和已经发出的模型请求无法原子撤回。收到失效通知后尽力取消相关运行，但不承诺删除与远端生成之间存在一个全局原子事务。已经显示的其他会话回答、手工复制和历史导出包是独立副本。

删源后依赖它的派生摘要要失效/重建，引用显示“来源已删除”。保留的独立用户记忆移除来源正文摘录并标记不可定位；用户如需忘记该长期事实，应同时删除相应记忆条目。

## 17. 存储、任务、备份与恢复

服务数据目录独立于见涨应用目录和源码仓库，位置可配置：

```text
memory-data/
  instance.json                       serviceId 和数据格式信息，无令牌明文
  memory.sqlite                       用户、业务数据、索引、任务和墓碑
  files/<userId>/<documentId>/<versionId>/
  staging/<userId>/                    未发布的上传和解析产物
  exports/<userId>/                    短期导出产物
```

首版一个服务实例管理一个本地数据目录，SQLite 开启外键和合理事务策略。全文索引和向量必须随正文删除同步失效；SQL 条件、对象文件路径和缓存键都包含用户归属。文件目录不直接通过静态 Web 路由公开。

如采用 WAL，数据库必须在本地支持的文件系统，不通过网络盘让多个服务器直接共享同一文件；WAL 的多进程访问有同主机约束。[SQLite WAL](https://www.sqlite.org/wal.html)

解析、摘要、向量化使用 SQLite 持久任务队列和有限并发 worker，API 进程负责接收/查询。先不引入分布式任务平台；任务租约、源 revision 和幂等键保证崩溃后可重试且不覆盖新数据。

备份分两类：

- 用户导出：只包含该用户的画像、已同步会话副本、文档、归属和版本清单，不包含其他用户、服务凭证及模型密钥。
- 本地管理员整实例备份：用于迁移/灾难恢复，包含所有用户，必须与普通用户导出接口分开。

用户导出采用带格式版本、校验哈希和清单的归档。数据库读取使用一致性快照；导出期间固定文档版本，阻止清理正在导出的文件，完成后再释放。不能只复制一个使用中的 SQLite 主文件而忽略 WAL。[SQLite Backup API](https://www.sqlite.org/backup.html)

恢复先在暂存区验证，再明确替换当前目标用户的数据，保留恢复前副本；首版不做跨设备自动合并。不能通过导入包里的 userId 获得其他用户身份，目标用户由当前授权确定，源 ID 在验证后映射。

恢复后更新数据 epoch/代际，客户端旧同步队列需重新核对，不能把备份后已删除的会话自动补回。跨实例迁移同时处理 serviceId 与客户端连接绑定，需要显式确认，不只是改一个 URL。

见涨现有 JSON/Gist 备份保持原范围，新增连接令牌不进入普通备份。界面说明它不包含独立记忆服务的完整数据库和文件；记忆导出只能恢复已同步内容，不代表备份了见涨尚未同步的聊天。

## 20. 验收与测试设计

本节定义整体验收用例；其中一部分已有受控自动测试，但 D 的真实文件/界面人工验收和 B 的真实维护模型效果验收尚未执行。

1. 记忆关闭/服务未启动时，原 Provider 配置、聊天、股票工具和独立分析任务仍保持原路径；故障不阻塞普通聊天。
2. 用户 A、B 分别创建同名记忆、会话和文档，搜索、猜 ID 读取、下载、任务、导出及缓存均不能串数据。
3. 修改请求体 userId、agentId 或资料库 ID 不能扩大令牌绑定权限；撤销令牌后不可继续请求。
4. A 的会话保存长期偏好后，A 的另一会话及授权示例 Agent 下一轮可使用；B 不可见。
5. 同一用户的临时会话要求和专属附件不会自动进入其他会话；历史共享开关生效。
6. 旧维护任务不能覆盖用户新更正；删除条目后同一批历史消息不能立即重新生成它。
7. 消息重复/乱序/丢失确认、落盘后入队前崩溃和服务重启，均能按检查点恢复且不重复形成记忆。
8. 切换用户或更换同地址服务实例时，不把旧队列、上下文或旧会话发给新主体。
9. 在线删除会话清除副本、摘要、历史和附件；全局资料和独立用户记忆按说明保留。
10. 离线删除显示待同步，重连优先删；旧索引任务和事件不会复活已删除会话。
11. PDF/DOCX/TXT/Markdown 可按支持范围导入，命中正确版本和定位；扫描 PDF 如实显示需要 OCR。
12. 中文短词、股票代码、年份、同义表达和无关问题都有检索用例；没有依据时不能编造资料结论。
13. 替换文档失败保留旧活动版本，发布后不混用旧版本；删除文档后来源读取和新检索失效。
14. 向量或维护模型失败时显示实际降级状态，不丢原始消息，不错误推进维护检查点。
15. 真实 token 预算约束下不拆断工具调用序列，不让资料占满上下文；新来源类型不破坏原有官方引用。
16. 用户导出只含该用户且不含凭证，恢复后文档可定位、索引可重建，旧队列不会污染恢复结果。
17. 独立示例客户端使用同一标准 API 完成身份确认、注册会话、保存记忆、检索和删除，不读取见涨源码或数据库。

静态检查覆盖类型、边界、接口契约、存储约束、错误分支和测试代码。运行时通过假模型/受控服务验证并发和故障，再在授权后用真实模型和用户选定文件评估效果。

效果评估建立约 30–50 个固定问题，比较无记忆、关键词检索、混合检索，记录正确召回、错误注入、来源支持性、更新/删除有效性、延迟和调用成本。用户越界、删除后新读仍命中、旧写覆盖新事实是必须修复的问题；不在未实测时承诺准确率或固定响应时间。

## 21. 决策摘要与参考

本版固定的方向：独立本地服务、标准 HTTP 接入、令牌绑定用户、多用户隔离、见涨原 AI 路径不迁移、原 JSONL 保留并通过事件同步、服务独立维护/向量配置、资料与删除联动、后续能力不抢跑。

实施前只需确定私有工程实际位置和可用模型端点；端口、数据库目录和模型参数可配置，不影响上述架构。本文中的路径、CLI 和 API 均为设计，不应误读为已有实现。

参考资料：

- [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html)：HTTP 接口的可机器读取描述。
- [RFC 6750](https://www.rfc-editor.org/info/rfc6750/)：Bearer 凭证形式及 TLS 要求；本地开发例外不等于公网安全方案。
- [SQLite FTS5](https://www.sqlite.org/fts5.html)：全文索引和分词边界。
- [SQLite WAL](https://www.sqlite.org/wal.html)：并发与存储部署约束。
- [SQLite Backup API](https://www.sqlite.org/backup.html)：一致性数据库快照。

## 22. 记忆系统完成之后的后续步骤（本阶段不实施）

以下按建议顺序记录，完成并验收本地记忆功能后，再逐项讨论具体实现。现阶段不提前建设账号、支付或云端基础设施。

1. **复盘本地效果与服务成本。** 根据真实使用评估画像质量、历史检索、中文资料召回、维护频率、存储增长和模型消耗，确定哪些能力值得产品化。
2. **正式账号与身份绑定。** 再设计注册登录和登录凭证，让经过验证的登录身份映射到现有 userId；本地用户与账号的绑定必须验证控制权，不能仅按姓名自动合并。旧数据迁移和多设备关系另行确定。
3. **云端部署与隐私边界。** 再确定服务器、HTTPS、密钥管理、备份、运维和数据保留政策；部署迁移不只是修改地址，还要处理数据实例、凭证、用户映射及客户端队列。远程服务仍不接管见涨原有 AI，除非用户另行决定。
4. **订阅、授权、额度与支付。** 再决定免费/付费边界、套餐、并发和资源额度，所有付费权限由服务端执行；现有开源 AI 能力是否调整另行讨论，不在本阶段暗中加入收费门槛。
5. **更多 Agent 接入。** 基于已完成 HTTP 契约增加其他语言 SDK、MCP 适配、细粒度凭证和自建 Agent 生命周期封装；按实际需求决定是否在私有服务内部嵌入 MemoryEngine。
6. **规模化和高级资料能力。** 有数据支持后再选择更大规模数据库/向量索引、分布式任务、OCR、复杂表格和高阶重排，不先堆叠基础设施。
7. **发行与商业边界。** 再确认私有服务发布方式、客户端与服务协议、依赖许可证、品牌及企业部署要求。独立私有工程可以避免 GitHub 公开源码，但分发到他人电脑上的实现仍可能被分析；真正的云端核心保护需要只在自有服务端执行。

以上事项均为后续议题，不是当前记忆功能实现的前置任务。本阶段先把“可区分用户、可本地独立运行、可标准接入、可检索资料、可正确删除”的记忆系统做完整。
